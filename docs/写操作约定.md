# 写操作约定（三仓共用 · 一字不差）

> 波次 0 拍板（2026-11-14）。`booth-cloud` / `booth-agent` / `booth-web` 对外材料引用本节时不得改写口径。

## 写操作怎么走

用户在客服对话里表达退货、取消待付款、改地址等意图后：

1. Agent **先做校验**（身份、订单归属、状态是否允许办理）；
2. 校验通过后 **在对话内直接提交到商城网关**（直写），**不再弹出确认卡**，也不再走已废弃的 `POST /app/chat/confirm`；
3. 直写前受 **写熔断** 约束；直写须带 **参数指纹 + outbox 幂等**（波次 1 补挂），避免同一意图重复建脏单。

对外统一表述：**校验后直写 + 写熔断 + 指纹/outbox 幂等**。  
禁止再写「确认卡防误触」，除非产品恢复确认流。

## 流式体验

- 主路径：`booth-web` 客服走 `POST /app/chat/stream`（SSE），先推进度再推正文，降低干等感（**不宣称**未附出处的「约 50%」类数字）。
- 降级：SSE 不可用时回退同步 `POST /app/chat`。
- Agent 静态演示页与 Web 客服行为一致（直写 + SSE）。

## 明确不宣称

下列能力**不做、不写进亮点**（诚实边界，不是偷工减料借口）：

- MCP / 多 Agent / RAGAS / 完整 OpenTelemetry
- 呼叫中心 / 多店铺
- 真支付宝沙箱跑通（无密钥则只宣称 Mock + 接口预留）
- 凭证上传 / 金额试算 / 退款进度查询
- 演示站 httpOnly Cookie 会话（已知用 localStorage）
- 未实测的压测数字（如 1000 人秒杀）不当成已验证结论
