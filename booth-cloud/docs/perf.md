# 下单压测

场景与开发计划一致：200 个已登录会员同时对同一个 SKU 各下一件，该 SKU 库存 100。请求经过网关 `POST /trade/app/orders`。

本机没有安装 JMeter，这一轮用 `logs/step4-accept.ps1` 跑。`perf/order.jmx` 是同一接口的 JMeter 计划，换一台装了 JMeter 的机器可以复现。

| 项 | 结果 |
|---|---|
| 时间 | 2026-10-24 |
| 并发 | 200 个请求，同时在途约 40 个 |
| 成功下单 | 100 |
| 失败 | 100（库存不足） |
| 结束后实物库存 | 100 |
| 结束后锁定库存 | 100 |
| 全部请求完成耗时 | 29.3 秒 |
| 吞吐 | 6.8 请求/秒 |
| 响应时间 p50 | 5698 毫秒 |
| 响应时间 p95 | 11272 毫秒 |

成功数和库存一致，没有超卖。慢的原因是 200 个请求要抢同一行 SKU，锁定会排队，而且每次下单还要再调用户服务和商品服务。这个数字是开发机上的结果，不是单独压测机。

# 秒杀

本机没有安装 JMeter，没有跑计划里的 1000 人抢 100 件。`perf/seckill.jmx` 是这个场景的计划。实际用 `logs/step5-accept.ps1` 核对了超卖：秒杀库存 8，20 个已登录会员同时各抢 1 件。

| 项 | 结果 |
|---|---|
| 时间 | 2026-10-25 |
| 并发 | 20 个会员，同时发出抢购 |
| 抢到资格 | 8 |
| 结束后 Redis 剩余 | 0 |
| 结束后活动库存 | 0 |
| 有效秒杀记录 | 8 笔，合计 8 件 |
| 对账 | 一致 |

抢到资格的人数和库存一致，Redis 和数据库都没有出现负数。这轮没有单独统计 p50、p95 和吞吐，因为脚本只核对超卖和对账。

# 商品详情

200 个请求同时查同一个已上架商品的前台详情，经过网关 `GET /product/open/products/{id}`。同时在途最多 40 个。详情正文走本地缓存和 Redis；销量和可售库存每次仍查数据库，不放进 10 分钟缓存。这是同一次脚本里刚上架的商品，所以前面几个请求会先把缓存填上，后面的请求命中缓存。数字是这一整轮混在一起的结果。

| 项 | 结果 |
|---|---|
| 时间 | 2026-10-26 |
| 并发 | 200 个请求，同时在途最多 40 个 |
| 成功 | 200 |
| 失败 | 0 |
| 响应时间 p50 | 14 毫秒 |
| 响应时间 p95 | 135 毫秒 |

本机没有安装 JMeter，这一轮用 `logs/step6-accept.ps1` 跑。脚本没有统计吞吐。这个数字是开发机上的结果。
