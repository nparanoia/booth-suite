# 前六步做了什么

这篇是给自己复述用的：每一步做了哪件事，以及它要挡住的问题。接口细节和验收标准仍以 `docs/roadmap-step4-7.md` 为准，压测数字在 `docs/perf.md`。

系统是一个微服务电商。请求先到网关，再分到用户、商品、交易、搜索四个服务。会员走前台，管理员走后台，服务之间走内部接口。

## 第一步：工程骨架

五个服务如果各写各的启动方式、返回格式和数据库脚本，后面每加一个功能都要重新对齐。

这一步把工程拆成网关、用户、商品、交易、搜索，以及公共模块和对外的接口模块。公共模块统一了返回体、业务异常、分页、MyBatis 和 Redis。数据库变更用 Flyway，已经执行过的脚本不再改。本地用 Docker 起 MySQL、Redis、RabbitMQ、Nacos 和 Elasticsearch。服务通过 Nacos 互相发现。搜索服务这时只有一个能启动的空壳。

## 第二步：用户、商品和购物车

没有会员和商品，后面的下单没有对象。购物车如果自己存一份价格和库存，商品一改价，购物车里还是旧数字。

这一步做了会员注册、登录、资料和收货地址，以及后台的品牌、两级分类、属性和商品 SKU。前台只能看到已上架的商品，展示价取 SKU 里的最低价，实物库存不暴露给前台。购物车放在交易服务，商品名、规格、价格和可售库存每次向商品服务现查。服务之间的调用走 `/inner`，由调用方自动带上签名，下游不自己解析登录令牌。

## 第三步：认证和权限

后台接口如果只靠“调用方自己说我是管理员”，谁都可以改商品、改库存。会员也可以拿别人的编号去改别人的地址。

这一步把会员和管理员分成两套登录。管理员按角色拿权限码，网关校验令牌后，把身份和权限写进经过签名的请求头。下游只认这个头。改角色或禁用账号后，不用重新登录就生效。伪造身份头、绕过网关直连、用编码路径绕过 `/inner` 和 `/app`，都会被拒绝。会员令牌不能进后台，管理员令牌不能进前台。

## 第四步：交易

下单最容易错的地方有四个：很多人同时买最后一件会超卖；支付、扣库存、关单只成功一半，数据就对不上；优惠分摊会把某一行算成负数；取消时积分或优惠券先退、扣减后到，会把已经退回的又扣掉，或者把不该退的再退一次。

库存不直接减。下单时按订单号锁定，支付成功才扣减并加销量，取消或超时才释放。库存和状态都用条件更新，影响行数为 0 就当这次没成功。同一订单号重复锁、扣、放，数字只变一次。先收到释放、后收到锁定的，锁定会被拒绝。

订单从确认、提交、支付、发货、收货到关闭，走状态机。会员只能操作自己的订单。超时未支付由延迟消息关单。需要通知别的服务时，先在本地事务里写下消息，提交成功后再发到 RabbitMQ，避免数据库回滚了消息却已经发出去。

支付先验签，再对金额，最后才改状态。金额不对或签名不对，订单保持原样。重复通知不会重复扣库存。模拟支付默认关闭，本地验收要同时打开两个开关。仓库里没有支付宝沙箱密钥，沙箱支付没有实际跑过。

优惠券和积分可以抵扣。分摊在最后一行吃掉尾差，某一行变成负数时，把多出来的部分挪到还有货款的行上，每行实付不小于 0。取消订单会关单、释放库存，并退回积分和优惠券。积分如果退回发生在扣减之前，先写一条禁止标记，晚到的扣减看到它就不再改余额。

售后可以申请和按顺序审核。退款只记状态，不调用支付渠道。

200 个会员同时买库存 100 的同一件商品，成功数是 100。数字在 `docs/perf.md`。

## 第五步：秒杀

普通下单每来一次都要锁数据库里的库存行。秒杀时同一行会被打满，而且“先查再减”会超卖。人没付款就关掉页面，资格还得还回去，否则库存越卖越少。同一个人反复点，也不能超过限购。

活动开始前把秒杀库存放进 Redis。抢购时用一段 Lua 同时检查时间、限购和库存，通过才扣减。接口马上返回一个排队编号，真正下单由消息异步完成，秒杀价不能再用券和积分。抢购地址是一次性的，活动开始前拿不到。

Redis 扣减成功但消息没发出去时，才把库存加回去。确认超时只能说明结果未知，不加回，避免订单已经生成库存又被还掉。超时关单会归还数据库和 Redis。关闭后的记录不再占名额，同一个人可以再抢。

网关只限制提交抢购，每秒 25 次。看场次和查结果不占这个额度。交易服务再按每个秒杀商品每秒 20 次限制。被限流返回 429。对账比较 Redis 已售、有效秒杀记录和未关闭订单，对不上只打日志，不自动改数。

库存 8、20 人同时抢，成功 8 人，对账一致。1000 人抢 100 件这轮没有跑。

## 第六步：搜索和详情缓存

商品多了以后，用数据库做中文模糊查询又慢又不准确。详情如果每次都查库，打开商品页会把数据库打满；如果一直用缓存，改了名字顾客却还看到旧的。

搜索走 Elasticsearch，只索引上架商品。商品名、副标题和关键字做中文分词，可以按分类、品牌、价格筛选，也能按销量、价格和新品排序。翻得太深会拒绝，避免一次拉出过多命中。

商品、SKU、属性、品牌、分类一变，Canal 从 MySQL 的 binlog 读出来，发到 RabbitMQ。搜索服务收到后按商品当前状态重写索引。写入版本用更新时间，更旧的消息盖不掉新文档。下架或删除会从索引里去掉。

整库重建时先灌一份新索引，灌的过程中新变更也写进这份新索引，灌完再把别名切过去。搜索一直用别名，不用停。同一时间只允许一个重建。

前台详情先看本机内存（30 秒），再看 Redis（大约 10 分钟，再加一点随机时间，避免同时失效）。改商品提交成功后删掉 Redis，并通知各实例清掉内存，所以下一次打开就是新内容。销量和可售库存不放进这层缓存，每次现查数据库。不存在的商品会把“没有”缓存一小段时间，1000 次查询只打到数据库 1 次。

200 个详情请求同时在途最多 40 个，全部成功。p50 是 14 毫秒，p95 是 135 毫秒。前面几个请求会先填上缓存。

## 第七步：链路和计数

一笔订单从网关进到交易，再去问用户和商品，中间还有消息。慢了或者失败了，日志散在五个进程里，对不上是哪一次请求。下单成功了多少、失败了多少、秒杀被限了多少，也没有一个地方能直接看到。

这一步给一次请求一个链路编号。网关、交易、用户、商品，以及交易发出去的消息，都挂在同一个编号上。日志里带上这个编号。本地把采样率设成 1，所以一次下单就能在 Zipkin（http://localhost:9411）里看到整条链。服务之间的调用要额外带上 Feign 的观测包，否则下游会变成另一条链。

计数交给 Prometheus，看板在 Grafana（http://localhost:3000，账号 admin / admin）。看的是：下单成功、下单失败、经过网关的秒杀提交、被限流挡住的秒杀、本地消息重试、重试耗尽、秒杀对账对不上、订单已经关闭又收到支付成功。这些计数在服务启动时就是 0，事件发生才增加。秒杀对账自动修不好的才计数；库存对账自己修好的只打日志。

## 这些步骤合在一起解决的事

会员可以注册、看商品、加购物车、用券和积分下单、付款、取消和申请售后。管理员可以管商品、订单、优惠券和秒杀，并且只能做自己有权限的事。库存不会因为并发、重复通知或消息乱序被多扣。秒杀先在 Redis 里挡住超额请求。搜索能跟上商品变更，详情改完立刻是新的。一次下单能顺着同一个编号看完它经过的服务，业务计数可以在看板上直接读。
